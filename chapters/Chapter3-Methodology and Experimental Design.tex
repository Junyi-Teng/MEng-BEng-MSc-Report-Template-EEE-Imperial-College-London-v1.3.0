\section{Methodological Overview}
\label{sec:methodological-overview}
The experimental framework considers four principal quantization
routes. AWQ is used as a representative weight-only W4A16 approach,
while SmoothQuant provides a W8A8 reference in which both weights and
runtime activations are quantized. A project-specific W4A8 pipeline is
implemented to investigate the combined effect of 4-bit weight
compression and dynamic 8-bit activation quantization. NestQuant is
then used to extend the quantization scope further through progressively
broader configurations involving weights, activations and the KV cache.
The overall methodology is summarised in Figure~\ref{fig:methodology-overview}.

\section{Model and Experimental Context}
\label{sec:model-experimental-context}
\subsection{Base Model and Quantization Scope}
\label{subsec:model-quantization-scope}
Llama-3.2-3B-Instruct contains 28 Transformer decoder layers with a
hidden dimension of 3,072 and an intermediate feed-forward dimension of
8,192. The attention mechanism contains 24 attention heads and eight
key--value heads, with a head dimension of 128\cite{meta2024llama32}. This architecture provides a sufficiently large model for weight storage, activation
precision and KV-cache growth to represent meaningful deployment
constraints, while remaining practical for repeated calibration and
evaluation within the computational resources available to this
project.
The quantization scope was defined at the Linear-projection level.
Within each decoder layer, seven weight matrices were treated as the
principal quantization targets: the query, key, value and output
projections in the attention block, together with the gate, up and down
projections in the feed-forward network. This gives

\begin{equation}
N_{\mathrm{linear}}
=
28 \times 7
=
196
\label{eq:target-linear-modules}
\end{equation}

target linear modules across the complete model. The resulting scope
covers 2,818,572,288 weight elements. Table~\ref{tab:model-scope}
summarises the principal model dimensions and the corresponding
quantization treatment used throughout the experimental framework.

\subsection{Calibration Data}
\label{subsec:calibration data}
Two datasets were used for calibration and evaluation in this project:
UltraChat and WikiText-2. Their roles were deliberately separated
because post-training quantization requires representative data for
estimating quantization parameters, whereas final model quality should
be assessed using data that are not used to optimise those parameters.
The exact data protocol also differs between the reference
AWQ/SmoothQuant/W4A8 pipelines and the NestQuant experiments.

UltraChat was used primarily for the calibration and diagnostic
evaluation of the AWQ, SmoothQuant and project-specific W4A8 pipelines.
Calibration samples were drawn from the \texttt{train\_sft} split,
while the retained diagnostic evaluations used the
\texttt{test\_sft} split. For the latter, model quality was evaluated
only over assistant-response tokens rather than over the complete
conversation. This provides an instruction-following-oriented measure
of language modelling quality while ensuring that prompt tokens do not
dominate the reported loss.

WikiText-2 was used for the NestQuant calibration and final
language-model evaluation protocol. Contiguous sequences from the raw
training split were used to collect the statistics required for
sequential weight quantization, including the second-order information
used by the QA-LDLQ procedure. The calibration sequence length was set
to 2,048 tokens, consistent with the context length subsequently used
for evaluation. Within the calibration process, separate fit and
held-out windows were maintained: the fit windows were used to
construct the quantization parameters, while the held-out windows were
used to assess the resulting reconstruction objectives without
contributing to parameter selection.Although both datasets are used within the same experimental framework,they serve different methodological purposes and employ different scoring procedures. Their principal differences are summarised in

\section{Quantization Pipelines}
\label{sec:quantization-pipelines}
The quantization methods reviewed in Chapter~2 were implemented as
separate experimental pipelines around the same
Llama-3.2-3B-Instruct base model. The pipelines differ not only in
nominal bit width, but also in quantization scope, calibration strategy,
tensor representation and runtime execution path. AWQ and SmoothQuant
were used as reference implementations for weight-only and joint
weight--activation quantization, respectively. A project-specific W4A8
pipeline was then developed to investigate a more aggressive mixed-bit
operating point, while NestQuant extended the study to structured
vector quantization of weights, activations and the KV cache.

\subsection{Reference Pipelines: \acs{AWQ} and SmoothQuant}
\label{subsec:reference-pipelines}
AWQ was implemented as the weight-only reference pipeline using
Llama-3.2-3B-Instruct as the source model. The local quantization script
loaded the pretrained model in FP16 and applied a one-shot
post-training quantization procedure using the \texttt{llmcompressor}
implementation. UltraChat was used as the calibration source, with
samples drawn from the \texttt{train\_sft} split. Each conversation was
normalised into user--assistant messages and rendered using the native
Llama chat template before calibration.

The retained configuration used 64 calibration samples with a maximum
sequence length of 512 tokens. Quantization was applied through an
\texttt{AWQModifier} followed by a \texttt{QuantizationModifier} using
the W4A16 scheme. All eligible \texttt{Linear} modules were targeted,
while the tied language-model head, \texttt{lm\_head}, was explicitly
excluded. Activations were therefore not quantized by this pipeline and
remained at higher precision during inference.

The complete local procedure is illustrated in
Figure~\ref{fig:awq-pipeline}. The process begins from the common
full-precision model, prepares the UltraChat calibration conversations,
applies AWQ-based weight transformation and W4A16 quantization, and
finally serialises the resulting model as a compressed checkpoint.

The complete SmoothQuant implementation used in this project is
illustrated in Figure~\ref{fig:smoothquant-pipeline}. The pipeline is
divided into an offline calibration and smoothing stage and a runtime
W8A8 inference stage. During calibration, representative UltraChat
samples are used to collect activation statistics and determine the
channel-wise smoothing transformation. The transformed weights are then
represented at INT8 precision, while input activations are dynamically
quantized on a per-token basis during inference. The implementation
also shares activation quantization between projections that consume
the same hidden-state tensor, reducing redundant runtime quantization
operations.
\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.95\textwidth]
    {imgs/smoothquant-pipeline.png}
    \caption{SmoothQuant W8A8 quantization and runtime inference pipeline.}
    \label{fig:smoothquant-pipeline}
\end{figure}

In contrast to the AWQ configuration which reduces only the precision of the model weights, the SmoothQuant pipeline applies low-precision representation to both
weights and runtime activations. The implementation therefore provides
a reference point for evaluating the effect of extending quantization
from a W4A16 weight-only configuration to a W8A8 execution regime.

Representative activation statistics are first collected from the
UltraChat \texttt{train\_sft} calibration split. These statistics will be used to redistribute the part of the activation-range difficulty into the corresponding weight channels before low-precision execution.

Following smoothing, the target Linear projections are represented
using 8-bit weights, while their input activations are dynamically
quantized to INT8 during inference. Activation quantization is performed
on a per-token basis so that the quantization scale can adapt to the
numerical range of each runtime input. The resulting W8A8 Linear
operations were implemented using custom Triton kernels rather than
being evaluated only through an offline fake-quantization procedure.

To reduce redundant runtime quantization, projections consuming the
same hidden-state tensor were grouped where appropriate. In particular,
the query, key and value projections share one activation-quantization
operation, while the gate and up projections similarly share their
quantized input. This preserves the same numerical input for the
associated projections while reducing repeated activation-processing
overhead.
